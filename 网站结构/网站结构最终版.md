## 0. 结论先行

最终站点定位为：

> **以 Wiki 为入口、以实测决策攻略为核心的 Star Wars Zero Company 英文攻略站。**

首页承接 `Star Wars Zero Company Wiki / Guide` 品牌与泛需求；真正建设权重和回访价值的内容集中在四条用户路径：

1. **怎么选**：Classes、Hawks Build、Best Team、Respec。
2. **怎么打**：Walkthrough、Missables、Trophy Guide、Beginner Guide。
3. **怎么修**：PC Performance、FPS Fix、Steam Deck、System Requirements。
4. **怎么扩展**：Mods、安装与兼容性，但必须遵守来源、安全和补丁验证门槛。

本版以“版本2-哥飞版”的 Silo、SEO 基础、逐页规范和通用组件为主干，吸收 GPT 版以下亮点：

- 按发售后的真实搜索意图重排优先级，不再把 Release、Trailer、News 当主线。
- 合并高度重叠的关键词，避免一词一页和站内内耗。
- 为攻略增加游戏版本、平台、难度、剧透等级、验证日期和证据等级。
- 增加 Builds、Performance、Mods 的决策型页面模板。
- 首页由“长百科”改为快速分流 Hub，并预留轻量 Build Finder。
- 按 P0-A、P0-B、P1、P2 分期，先做最小但完整的内容闭环。

同时修正两版中的问题：

- 不再使用已过时的发售前结构重心。
- 不同时建立 `/` 和 `/wiki/`，避免首页 Wiki 意图互相竞争。
- 不同时建立 `/classes/best/` 与 `/classes/tier-list/`。
- 不把 Characters 和 Companions 建成两个内容高度重叠的 Hub。
- 不把 System Requirements、PC 优化、Steam Deck 和 Mac 全塞进一页。
- 不首发批量生成单成就、单任务、单模组等薄页。
- 不将社区猜测、第三方数据或未经实测的 Build 写成已验证事实。
- 修正旧稿中的 `/multplayer/`、`/companons/` 等拼写问题。

## 2. 目标用户与核心任务

| 用户阶段 | 用户问题 | 首选入口 | 网站应给出的价值 |
|---|---|---|---|
| 购买前 | 在哪玩、配置够不够、是否值得买 | Game Info、System Requirements、Worth It | 直接答案、平台差异、来源日期 |

- 不做泛 Star Wars 百科。

## 4. 全局导航与页面关系

### 4.1 顶部主导航

```text
Builds | Classes | Characters | Walkthrough | Trophies | Performance
```

右侧：`Search`。移动端收进抽屉，但 Search 保留为独立图标。

二级菜单或页脚收纳：

```text
Beginner Guide | Weapons | Mods | Game Info | System Requirements | Worth It | Multiplayer
```

主导航控制在 6 个核心入口，避免 GPT 版 7 个一级入口在中等宽度下拥挤。

### 4.2 面包屑

统一格式：

```text
Home > Cluster Hub > Current Page
```

例：

```text
Home > Builds > Hawks Build
Home > Performance > Steam Deck
Home > Walkthrough > Chapter Name
```

### 4.3 每页最少内链规则

每个可索引页面必须包含：

- 1 个父 Hub 链接。
- 2—4 个同集群相关页。
- 1 个跨集群的下一步链接。

推荐关系：

| 当前页 | 必链页面 |

### P1：形成主题权重

- 8 个标准职业页。
- 有真实实测的 Operator Build 页。
- Runa 等高需求角色实体页，角色资料与 Build 不混写。
- Bonds、Permadeath、Advantage、Focus 等机制页。
- Weapons Hub；具体武器页必须有足够数据与独立搜索意图。
- 逐章 Walkthrough、Missables、Choices and Consequences、Endings。
- PS5 Performance。
- Mods Install；有真实兼容信息后再拆 Performance Mods 等子页。

### P2：只由 GSC、站内搜索或稳定数据源触发

- 单个成就页。
- 单个 Boss、Choice、任务支线页。
- 单个 Mod 的兼容性页。
- Steam Machine 独立性能页。
- Player Count / Steam Charts 时效数据页。
- Russian localization、多语言目录。
- Pong Krell、Order 66 等 Lore 页。
- Mac、Switch、G2A 等低深度独立页。

### P2 拆页门槛

满足以下任一条件才考虑拆页，并且仍需通过内容证据门槛：

1. GSC 同一意图查询在连续 28 天内形成稳定 impressions，且当前父页无法准确满足。
2. 站内搜索/用户反馈反复出现同一具体问题。
3. 内容主体至少能提供一个独立答案、表格、流程或实测，而不是两三句话。
4. 拆页后不会与现有页面竞争同一个主意图。

## 9. 全站信任与证据体系

这是最终版相对哥飞版最重要的补强。

### 9.1 页面头部统一字段

```text
Game Version
Platform
Difficulty
Spoiler Level
Last Verified
Evidence Level
Status
```

### 9.2 Evidence Level

| 等级 | 含义 | 页面写法 |
|---|---|---|
| `official` | EA、Steam、StarWars.com 等一手来源 | “Official”并链接原页 |
| `tested` | 自己在明确平台和补丁下完成验证 | 写测试环境、方法和结果 |
| `community` | 玩家报告或第三方实测 | 写来源、样本限制，不升级成官方事实 |
| `unverified` | 尚未确认或只有单一说法 | 明确标注；默认不索引 |

### 9.3 Status

```text
draft
verified
needs-retest
archived
```

规则：

- `draft`、内容不足和 `unverified` 页面默认 `noindex,follow`，不进入 sitemap。
- 补丁改变机制、Build 或 Mod 兼容性后，页面改为 `needs-retest`。
- `needs-retest` 可以保留索引，但必须在首屏显示过期提醒；若核心答案已不可靠则临时 noindex。
- 页面只有“最后验证日期”真实变化时才更新 `dateModified`。
- 不能把抓取失败、没有测试或没有找到信息写成“0”或“没有”。

### 9.4 页面底部统一块

```text
What Changed
Testing Notes
Official Sources
Community Evidence
Report Outdated Information
```

## 10. SEO 与索引规则

### 10.1 URL

- 全部小写、英文、连字符。
- Canonical 统一使用无尾斜杠格式；站内链接和 sitemap 保持一致。
- 一个搜索意图只有一个 Canonical 页面。
- 年份不写进 URL。

### 10.2 Title / Description / H1

- 主词靠前，优先准确表达任务，不机械追求固定字符数。
- H1 与 Title 同义但不必逐字重复。
- 年份只在内容确实持续更新且页面展示更新时间时使用。
- Description 说明页面能解决什么问题，不堆关键词。

### 10.3 Indexability

应索引：

- 有独立用户价值、完整回答、真实证据和稳定 Canonical 的公开页面。

应 noindex：

- 草稿、站内搜索结果、筛选组合页、空标签页、未验证生成页、薄内容页。

Sitemap 只包含：

- 返回 200、self-canonical、允许索引、已达到发布门槛的 URL。

### 10.4 Structured Data

| 页面 | 建议 Schema |
|---|---|
| 首页 | `WebSite` + `Organization`；`VideoGame` 可作语义补充 |
| Hub / 列表 | `CollectionPage` 或 `ItemList` + `BreadcrumbList` |
| 攻略 / Walkthrough | `Article` + `BreadcrumbList` |
| 视频页面区块 | 内容真实可见时用 `VideoObject` |
| 原创评测 | 仅在确实有原创评测时使用 `Review` |

FAQ 内容必须真实显示在页面上；不要把 FAQ Schema 当作保证富摘要的手段。不要为抓取来的聚合评分伪造 `AggregateRating`。

## 11. 通用组件清单

### P0 必需

1. `SiteHeader`：6 个主导航 + Search。
2. `SiteFooter`：按 3 个主题集群组织链接 + 非官方站免责声明。
3. `Breadcrumbs`：可视面包屑 + Schema。
4. `MissionBriefing`：开头直接给结论。
5. `EvidenceBadge`：Official / Tested / Community / Unverified。
6. `VerificationMeta`：版本、平台、难度、剧透、日期。
7. `RelatedPages`：父级、同集群和下一步链接。
8. `SpoilerGate`：轻度/重度剧透折叠。
9. `ComparisonTable`：职业、Build、武器和配置对比。
10. `SourceList`：来源名、发布者、链接、检查日期。
11. `ChangeLog`：版本变化与重测记录。
12. `FAQAccordion`：只承载可见 FAQ。

### P1 增强

1. `BuildFinder`：静态规则，返回证据与完整攻略链接。
2. `ClassMatrix`：职业×场景对比。
3. `SquadSlots`：四人阵容、替补和角色职责。
4. `AchievementTable`：筛选 Missable / Story / Difficulty 等。
5. `PerformanceTable`：测试硬件与补丁维度。
6. `WikiSearch`：搜索角色、职业、任务、成就和问题。

### 实现原则

- 内容与数据分离，不把大段正文和全部数据库硬编码在页面组件中。
- 表格移动端横向滚动，首列可冻结。
- 所有页面首屏优先显示答案，不先铺背景故事。
- 任何互动组件在 JavaScript 失败时仍能访问核心内容。

## 14. 建站验收标准

### 信息架构

- 首页、导航、页脚和 sitemap 使用同一套 Canonical URL。
- 不存在 `/wiki` 与首页、`best` 与 `tier-list` 等重复意图页面。
- 每个页面有唯一父 Hub，面包屑可回到父级。
- P2 页面未过门槛前不会批量生成空页面。

### 内容

- 每个 P0 页面首屏都有直接答案或下一步入口。
- 每个 Best / Build 结论都有版本、平台、难度和替代方案。
- 每个 Walkthrough 有剧透等级、Missable 和验证补丁。
- 每个 Performance Fix 有风险级别、回滚方法和副作用。
- 每个 Mod 只链接原作者或可信平台，并有补丁兼容状态。

### SEO

- 可索引页返回 200、self-canonical、允许索引且进入 sitemap。
- Draft、筛选页、站内搜索和未验证页 noindex，不进入 sitemap。
- Title、Description、H1 与页面任务一致。
- 结构化数据与页面可见内容一致，不伪造评分或 FAQ。

### 体验

- 移动端首屏能看到答案或主 CTA。
- 表格可横向滚动，核心列不会完全丢失。
- Search 能定位职业、角色、任务、成就和技术问题。
- 剧透内容默认受控，核心导航不依赖 JavaScript。

### 信任

- 页面显示 Last Verified，而不是统一伪造全站更新时间。
- Official、Tested、Community、Unverified 清楚区分。
- 补丁后受影响内容能批量标记 `needs-retest`。
- 页脚包含：`Unofficial fan-made guide. Not affiliated with EA or Lucasfilm.`

## 15. 最终执行建议

后续推进网站建设时，按以下顺序工作：

1. 先建立全局路由、导航、页面元数据和证据字段。
2. 完成 P0-A 的 14 个 URL 骨架，但只让达到内容门槛的页面索引。
3. 优先填充 Classes、Hawks Build、Best Team、Walkthrough、Trophy、PC Performance 六个核心资产。
4. 用 Game Info、System Requirements、Multiplayer 补齐基础事实闭环。
5. 有真实数据后再启用 Build Finder。
6. 根据 GSC、站内搜索和用户反馈逐步开放 P1/P2，不按关键词表机械批量建页。

最终的内容资源建议配比：

```text
职业与 Builds          35%
流程与成就             25%
性能与 Mods            25%
角色与购买基础信息      15%
```

这份结构是后续建站的默认基线。若开发过程中出现新搜索意图，先判断应该增强现有 Canonical 页面，只有通过拆页门槛后才新增 URL。
